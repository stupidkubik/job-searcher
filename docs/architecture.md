# Исследование архитектуры `job-searcher`

## Готовый файл

Подготовлен отдельный Markdown-документ, готовый к добавлению в репозиторий, например как `docs/architecture-and-roadmap.md`.

Файл содержит полный разбор текущего состояния, сравнительную таблицу вариантов хранения, целевую файловую структуру, подробную схему `jobs.csv`, модель `status + stage_reached`, миграционные команды для v1, план v2, Mermaid-диаграммы, шаблоны `application.md` и `profile.md`, CI/automation, интеграции и roadmap с оценкой трудозатрат.

## Ключевой вывод

Для этого проекта наиболее рациональна архитектура **CSV + Markdown**: `data/jobs.csv` как единственный структурированный source of truth и `applications/*.md` для длинного контекста конкретных вакансий. Это хорошо совпадает с природой job tracker: Indeed рекомендует вести структурированные поля по вакансиям, датам, статусам, follow-up и использованным материалам, а LinkedIn прямо советует отслеживать отклики в таблице с датами и заметками. citeturn9view0turn9view1

SQLite технически сильнее по типизации, constraints и SQL-аналитике и хорошо подходит как локальное хранилище приложения, но на нынешней стадии это преждевременная сложность: основная ценность текущего Git-based workflow — прозрачные текстовые изменения и простота ручного/автоматического редактирования. SQLite логичнее рассматривать позже, если появятся собственный UI, несколько связанных сущностей или конкурентные writers. citeturn9view3

GitHub Issues в исследовании предлагаются не как база, а как возможный будущий **intake/UI layer**: например, Zapier или ручной ввод создаёт Issue, а workflow преобразует его в проверенный PR к `jobs.csv`. Это сохраняет GitHub UX, не превращая Issues/labels в неявную реляционную модель.

## Что обнаружено в текущем репозитории

README и фактическая реализация уже расходятся. README объявляет `data/jobs.csv` основной базой и задаёт схему с `original_url`, `source_url`, `remote_policy`, `match_score`, `decision_reason`, `cv_version` и другими полями. fileciteturn1file0 Фактический файл находится не в `data/`, а в корне как `02-applications.csv`; его схема использует `work_format`, `job_url`, `fit_score`, `resume_version`, `why_fit`, `risks_or_gaps`, `next_action` и другие поля, а placeholder-запись имеет статус `Researching`. fileciteturn7file0

Одновременно `04-weekly-review.md` использует ещё одну модель воронки: `Researching → Ready to apply → Applied → Recruiter screen → Interview → Test task → Offer`. fileciteturn8file0 Поэтому в документе предлагается разделить две разные сущности:

```text
status        = текущее состояние заявки
stage_reached = максимальная достигнутая стадия воронки
```

Например:

```text
status = Rejected
stage_reached = Final interview
```

Это существенно полезнее для аналитики, чем один статус `Rejected`.

Также README предлагает ID на основе `normalized-company|normalized-role`, тогда как реальный CSV уже начинается с `001`. В исследовании аргументирован переход к immutable ID:

```text
job-0001
job-0002
job-0003
```

Название компании и вакансии при этом можно исправлять, не ломая ссылки и историю.

Отдельно подтверждён CV-хаос: в `cv/` одновременно находятся многочисленные варианты резюме, `copy`/`copy 2`, company-specific CV, cover letters, application PDF, psychometric PDF, русские и английские версии, а актуальное `evgenii-rubin-cv-08-2026.pdf` лежит в корне. В репозитории также присутствуют `.DS_Store` и файл `MargaritaSavonevskayaCV.pdf`; содержание последнего и psychometric PDF не анализировалось, поэтому в документе они помечены как требующие ручной проверки перед сохранением или удалением. fileciteturn6file1

## Рекомендуемое направление

Предлагаемая v1 сводится к тому, чтобы сначала сделать систему **непротиворечивой**, а не сложной:

```text
README.md
config/profile.md
data/jobs.csv
applications/
cv/current/
cv/archive/
templates/
reports/weekly/
scripts/
docs/
.github/workflows/
```

После этого v2 добавляет `validate.py`, детерминированный и fuzzy dedupe, `report.py` и небольшой CI. Интеграции предлагается начинать с ATS, где есть нормальные публичные интерфейсы: Greenhouse предоставляет публичные GET-endpoints Job Board API, а Lever — публичный Postings API для опубликованных вакансий. citeturn9view4turn9view5

LinkedIn разумнее оставить discovery-источником: его собственный tracker уже поддерживает пять стадий и заметки, но удаляет записи спустя год, а официальный Job Posting API предназначен для одобренных партнёров, что делает его плохой фундаментальной зависимостью для персонального tracker. citeturn9view2turn9view6

Zapier имеет смысл только после появления стабильного write path: webhook → intake → validation → PR, а не прямое изменение CSV. Такой подход сохраняет данные проверяемыми и уменьшает риск того, что внешняя автоматизация обойдёт правила схемы. citeturn9view7

В итоговом roadmap **v1 оценена примерно в 5–8 часов, v2 — ещё в 7–12 часов**. Главный архитектурный принцип документа: **не строить собственный ATS для одного человека; построить надёжный личный журнал поиска работы с Git как audit trail**.

## Текущая архитектура v1

Исследование выше зафиксировало исходное состояние. Реализация v1 уточнила его до
следующих инвариантов:

- `data/jobs.csv` — единственный структурированный источник истины; стабильный ID
  имеет вид `job-NNNN` и не зависит от названия компании или роли.
- `status` хранит текущее состояние, а `stage_reached` — наивысшую достигнутую
  стадию. Это позволяет отличать отказ после ATS от отказа после финального
  интервью.
- `applications/<id>.md` хранит длинный контекст: выдержки из JD, доказательства
  соответствия, ответы формы и хронологию. В CSV не допускаются переводы строк.
- Запись создаётся и меняется через `scripts/jobs.py`. Скрипт проверяет схему,
  даты, enum-значения, обязательные поля и ссылки на дубли до атомарной записи.
- Дедупликация идёт по каноническому `original_url`, затем по нормализованным
  company + role, затем через fuzzy-проверку похожих ролей в той же компании.
  Сомнительное совпадение не удаляется автоматически: его нужно подтвердить как
  `Duplicate` или добавить с `--force`.
- Для откликов используются только файлы из `cv/current/`; архив не является
  источником активных материалов.

CI запускает `validate` и unit-тесты на push и pull request. Fuzzy-поиск дублей
остаётся неблокирующим сигналом: похожие роли одной компании иногда являются
разными вакансиями.
